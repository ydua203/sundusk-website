# Day 1 — build notes

What landed and why, plus exactly what to run to verify it. Keep this file
as the running log the spec's build order (section 12) expects.

## What was built

- Next.js **15.5.23** (pinned — `create-next-app` defaults to 16.x now,
  downgraded to match spec section 2), App Router, TypeScript strict, ESLint.
- Tailwind v4 design tokens in [app/globals.css](../app/globals.css):
  the six brand colours as `@theme` vars (`bg-sand`, `text-espresso`, etc.),
  border-radius forced to `0` project-wide, box-shadow tokens neutralised.
- Fonts wired in [app/layout.tsx](../app/layout.tsx) via `next/font/google`:
  Fraunces (variable, optical-sizing axis enabled — see note below) and
  Hanken Grotesk (300/400/500/600).
- Drizzle schema in [db/schema.ts](../db/schema.ts) — all 7 tables from spec
  section 5, plus:
  - the `order_number_seq` Postgres sequence (starts at 1001) driving
    `orders.order_number`'s default (`'SD' || nextval(...)`), so order
    numbers are generated by Postgres, never application code
  - CHECK constraints on enum-shaped columns (`category`, `size`, `status`)
    and on money/quantity columns being non-negative — belt-and-braces on
    top of the Zod validation that'll sit at the API boundary later
  - Row Level Security enabled on `customers`, `addresses`, `orders`, each
    with a single `SELECT ... USING (auth.uid() = ...)` policy. No write
    policies exist anywhere — all writes happen through server routes using
    `SUPABASE_SERVICE_ROLE_KEY`, which bypasses RLS.
- Migration generated at `drizzle/0000_colossal_lady_bullseye.sql` (not yet
  applied to a database — see "What you need to do" below).
- Seed script at [db/seed.ts](../db/seed.ts) — 6 placeholder tops, 5 size
  variants each (XS–XL), stock 10 per size. Upserts on rerun, so it's safe
  to run more than once.
- `.env.example` (committed, no secrets) and `.env.local` (gitignored,
  currently blank — see below).
- A bare `/` page proving the fonts and palette actually load — not the
  real homepage, that's day 2.

### One deliberate deviation from the literal spec text

Section 3 asks for Fraunces "weights 400/600/700, optical sizing on."
Those two instructions are in tension: Google's optical-sizing axis (`opsz`)
only ships on the **variable** font file — requesting fixed static weights
via `next/font/google` silently drops the axis (verified against the
`next/font` Google metadata bundled in `node_modules`). I loaded Fraunces
as `weight: "variable", axes: ["opsz"]` to get real optical sizing, and the
app only ever sets `font-weight: 400/600/700` in CSS/Tailwind — so visually
you get exactly the three weights the spec asks for, with the optical-size
axis actually functioning (small headings stay crisp, large display type
gets the wider, warmer cut) rather than being silently inert.

## What you need to do

You said you already have Supabase (and eventually Razorpay/Resend)
credentials. Day 1 only needs **Supabase**. Two ways to get them into the
project — pick whichever you're comfortable with:

1. **Paste them to me in chat** and I'll write `.env.local` directly, or
2. **Edit `.env.local` yourself** (already created, currently blank —
   just fill in the four Supabase lines) and tell me when it's done.

Values needed (spec section 4):
```
NEXT_PUBLIC_SUPABASE_URL=          # Project Settings -> API -> Project URL
NEXT_PUBLIC_SUPABASE_ANON_KEY=     # Project Settings -> API -> anon public key
SUPABASE_SERVICE_ROLE_KEY=         # Project Settings -> API -> service_role key
DATABASE_URL=                      # Project Settings -> Database -> Connection string -> URI
                                    # Toggle to "Transaction pooler" (port 6543) first.
```

Once `.env.local` has those four values, run, in order:

```bash
npm run db:migrate   # applies drizzle/0000_*.sql to your Supabase database
npm run db:seed      # inserts 6 products x 5 variants (stock 10 each)
npm run dev           # starts the dev server
```

### What you should see

- `npm run db:migrate` — logs each statement, ends without error. If it
  complains about SSL, append `?sslmode=require` to `DATABASE_URL`.
- `npm run db:seed` — prints one `✓ <Product Name> (<slug>) — 5 variants
  seeded` line per product, six total, then `Seed complete.`
- In the Supabase dashboard → Table Editor: `products` has 6 rows,
  `product_variants` has 30 rows (6 × 5), each product's row in `products`
  has `category = 'tops'`.
- In Supabase → Authentication → Policies: `customers`, `addresses`, and
  `orders` each show RLS **enabled** with one `SELECT` policy.
- `npm run dev`, open `http://localhost:3000` — you should see a page
  reading "Sundusk" in a serif display face (Fraunces), a palette swatch
  grid of the six brand colours, a body-copy sample in Hanken Grotesk, and
  a sharp-cornered espresso button that turns terracotta on hover. Tab to
  the button — you should see a visible terracotta focus ring, not a
  stripped outline.

## Known, accepted issue

`npm audit` reports 3 high + 4 moderate CVEs, all inside Next 15's bundled
build-time tooling (`postcss`, `sharp` used during `next build`/image
optimisation; `esbuild`'s dev-server in `drizzle-kit`'s dependency chain).
None are reachable by a site visitor at runtime, and the fix in every case
is "upgrade to Next 16," which breaks the spec's Next 15 pin. Revisit when
the project is ready to move off Next 15, or when eslint-config-next /
drizzle-kit ship patched sub-dependencies within the 15.x line.

## Also start today: Resend domain verification

can take hours — it's not code, so I can't do it for you, but start it now
so it's ready by day 8 (emails):

1. In Resend, add `sundusk.in` (or whatever domain you'll send `hello@` from)
   as a sender domain.

   registrar.
3. Wait for Resend to show the domain as verified before day 8 — a Gmail
   address cannot be used as the `from` address (spec section 4).
